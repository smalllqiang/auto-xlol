# Playbooks：危机场景的确定性应对

`docs/doctrine.md` 说目标与原则；本文件说**出了事怎么办**。每个场景写清四件事：

1. **触发信号**：从哪个页面 / 哪个事件字段看出来；
2. **代码现在会做什么**：确定性行为，不猜测；
3. **人工要做什么**：在代码覆盖不到的地方，人按这里的步骤处理；
4. **缺口**：还没自动化的部分，对应路线图任务。

本期（AI-0）只写文档和已有的确定性应对，**不接模型、不新增自动支出**。

## 通用约束

- **告警不改支出**：`autoplay/reactions.py` 只产出 `alert` / `info`，从不决定花钱
  （ADR-009）。想让它停下来，用 `--pause-on-alert`。
- **急停**：写 `state/STOP`（或用看板 `s`），守护在下一轮退出；所有 `--execute`
  脚本也会拒绝动手。确认安全后删掉文件再启动。
- **单写者**：同一账号不要开第二个写进程；看板、报表、探险报告都是只读，可以随时跑。
- **判断「是否还活着」**：看 `state/daemon.json` 的 `updated_at`，不要只看
  `daemon.lock` 里的 pid。
- **别急着重试**：被游戏拒绝的动作不自动重试；先看 journal 里的 `evidence`。

## 场景一览

| 场景 | 触发信号 | 严重度 | 现在是否自动处理 |
| --- | --- | --- | --- |
| 被侦察 | 消息分类 0（间谍）未读增加 | alert | 只告警 |
| 来袭 / 战斗 | 消息分类 3（战斗）未读增加 | alert | 只告警 |
| 爆仓 | 资源占用 ≥ 阈值 / `storage_full` | info | 规划器已降级产出建筑 |
| 电力转负 | `energy_deficit` / 产量表 911 净产为负 | alert（事件）/ 规划器优先补电 | 部分 |
| 队列空转 | 建造/科研/船坞都空闲且无可负担候选 | info | 自动跳过，不空转下单 |
| 探险损失 | 舰队未归 / 探险报告显示损失 | 无事件 | 只读报告 |
| 采集断档 | `snapshot_gap` | alert | 只告警 |
| 连续被拒 | journal 连续 `ActionRejected` | 无事件 | 记日志、不重试 |
| 星球丢失 | `planet_lost` | alert | 只告警 |

## 1. 被侦察（间谍报告）

- **触发信号**：`state/events.jsonl` 里 `kind=message_new`、`category=0` 的未读数增加；
  `reactions.py` 判为 `alert`（`ALERT_MESSAGE_CATEGORIES = {0, 3}`）。
- **代码现在会做什么**：写一条 alert 到 journal；如果守护带了 `--pause-on-alert`，
  当轮暂停执行。看板「告警」栏会显示「收到间谍报告：新增 N 条，未读 M」。
- **人工要做什么**：
  1. 看板第 3 个 tab（消息）读报告正文，确认被谁侦察、侦察了哪个星球；
  2. 判断是否需要收缩：把资源花掉（下一条可负担候选）、把舰队派出去探险/运输，
     或用市场寄存（📘 攻略，本实例 `market` 已禁用，无法用）；
  3. 若确认危险，写 `state/STOP`，把守护停掉再处理。
- **缺口**：P2-2「舰队与威胁响应」还没做——目前不会自动转移或收缩，也不会分辨
  「被侦察」和「只是路人扫图」。**不要**把 alert 当成必须停机的信号。

## 2. 来袭 / 战斗报告

- **触发信号**：`message_new`、`category=3`（战斗）；或 `planet_lost` 事件。
- **代码现在会做什么**：alert；`--pause-on-alert` 时暂停当轮。
- **人工要做什么**：
  1. 消息 tab 读战报，看是胜是败、损失了什么；
  2. 看资源与舰队页面（看板第 1 个 tab），确认有没有被抢资源、舰队是否还在；
  3. 有连续来袭风险时停下守护（`state/STOP`），避免边打边按计划花钱。
- **缺口**：同样属于 P2-2。没有自动召回、没有自动补防御、没有威胁评分。

## 3. 爆仓

- **触发信号**：概览资源量 / 产量表容量 ≥ 100%；事件 `storage_full`（默认阈值 95%，
  跨过时触发一次，`severity=info`）。
- **代码现在会做什么**：
  - 规划器把该资源的产出建筑回本置 `null`、排到末尾，`notes` 汇总「已超仓容」；
  - 不把「资源不涨」当成异常，也不会因此报警。
- **人工要做什么**：
  1. 正常情况**不用管**：当前账号被赠送过大量资源，长期爆仓是已知状态；
  2. 想恢复产能就消耗或运走资源（造舰队、探险、仓库升级）；
  3. 只有「爆仓且三个队列都空、也没有可负担候选」时才需要人介入。
- **缺口**：没有「自动消耗溢出资源」的策略（属于策略扩展，不是 bug）。

## 4. 电力转负

- **触发信号**：
  - 事件 `energy_deficit`（alert），或
  - 产量表 911 的 `total`（净产）为负——规划器会写 `notes`「电力净产为负」并给
    幽能发电站 `priority=1`。
- **代码现在会做什么**：把幽能发电站排到产能候选最前（若买得起）；其它候选照常。
- **人工要做什么**：
  1. 先确认不是误读：产量表 911 净产为负 = 三厂消耗大于发电；
  2. 📘 按攻略降某个厂的生产比例（写入未封装，只能手动在页面改）；
  3. 或补电：发电站（代码会推荐）、📘 太阳能卫星（本实例未接入）。
- **缺口**：生产比例写入未封装，代码不能自动降耗；缺电只会「优先补电」，不会
  精确计算需要多少电力。注意幽能是速率资源，**不要**拿概览的 911 数值判断缺口
  （见 `docs/doctrine.md`）。

## 5. 队列空转（没有任何可执行候选）

- **触发信号**：事件 `queue_empty`（info）；或看板「候选」栏为空、日志连续多轮
  「skip / no affordable action」。
- **代码现在会做什么**：跳过，不重复下单，不做无谓请求重试。
- **人工要做什么**：
  1. 看 `notes` 与候选的「缺口」判断是资源不足、前置未满足，还是全部被预算/allow-list
     挡掉；
  2. 若阶段目标的前置解析失败（`notes` 里有「无法解析」），去页面核对文案并修解析器；
  3. 若只是资源不够，等采集或调整 allow-list。
- **缺口**：没有「等待资源」的显式状态提示，只能从 notes 推断。

## 6. 探险损失 / 舰队未归

- **触发信号**：`scripts/expedition.py` 报告里航道与舰队对不上；舰队表里探险队
  长时间未回；或探险报告显示损失（当前不采集战报正文）。
- **代码现在会做什么**：只读报告 + 循环发送/召回；每轮重读报告，队列忙就不发。
- **人工要做什么**：
  1. 跑 `.venv/bin/python scripts/expedition.py --no-verify-ssl` 看航道与在途舰队；
  2. 用 `scripts/dispatch_expedition.py` 预览，确认后再决定要不要补队；
  3. 若长时间丢失，检查是不是 `stay_time` 非法（必须 1..探险技术等级）。
- **缺口**：不采集战报正文，无法自动归因损失原因。

## 7. 采集断档 / 服务不可达

- **触发信号**：`snapshot_gap` 事件（采集间隔超过阈值）；守护日志出现网络错误、
  退避重试。
- **代码现在会做什么**：指数退避（`--backoff-base` / `--backoff-max`），连续失败
  超过 `--max-failures` 退出；断档写 alert。
- **人工要做什么**：
  1. 先看 `state/daemon.json` 的 `updated_at`，判断是守护挂了还是网络问题；
  2. 证书过期是本实例常态，脚本要带 `--no-verify-ssl`；
  3. 采集断档期间**不要**手工执行写操作，避免和守护抢写。
- **缺口**：没有外部健康检查；靠看板和心跳人工发现。

## 8. 连续被拒（`ActionRejected`）

- **触发信号**：journal 里 `ActionRejected` 连续出现；看板日志显示「拒绝」。
- **代码现在会做什么**：不重试；`before_post` 预检查拒绝会让本轮换下一条候选
  （ADR-012）；其余拒绝只记录并结束本轮。
- **人工要做什么**：
  1. 读 journal 的 `evidence`（页面给出的理由）；
  2. 常见原因：研究进行中升科研实验室、资源其实不够（页面缺口）、前置未满足、
     队列已满；
  3. 确认是稳定的规则（不是临时状态）就修执行器/规划器，并补测试。
- **缺口**：没有按原因分类的统计视图，只能 `jq` / `state_report` 看。

## 9. 星球丢失（`planet_lost`）

- **触发信号**：事件 `planet_lost`（alert）。
- **代码现在会做什么**：alert；该轮仍可能继续执行其它动作。
- **人工要做什么**：停下来（`state/STOP`），核对星球列表与舰队，确认是不是放弃
  殖民地之类的正常操作导致的误报，再决定是否恢复守护。
- **缺口**：没有多星球调度（P2-3），丢失后不会自动切换星球。

## 维护方式

- 新增一个自动应对：先在本文件写清触发信号与代码路径，再改 `reactions.py` 或
  对应执行器，最后补测试。
- 场景消失（页面改版、模块禁用）：把条目改成「已不适用」并注明日期，不要删除——
  换实例时还要用。
